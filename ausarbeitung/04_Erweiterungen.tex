\begin{section}{Erweiterungen für MOROS}

Damit MOROS die Grundlage für ein interaktives und verteiltes Spiel werden konnte, mussten mehrere Komponenten ergänzt oder erweitert werden.
Im Ausgangszustand bietet MOROS lediglich eine Shell, ein Dateisystem und rudimentäre Netzwerkunterstützung.
Folgende Erweiterungen waren notwendig, um die Spielmechanik und die Netzwerkkommunikation umzusetzen:

\begin{itemize}
    \item \textbf{Framebuffer:} für die grafische Darstellung von Spielfeld, Spielern und Objekten.
    \item \textbf{PS/2-Maus:} um eine zweite Eingabequelle neben der Tastatur zu haben und Zielen/Schießen zu ermöglichen.
    \item \textbf{UDP-Erweiterungen:} um Kommunikation zwischen Server und Clients über das Netzwerk zu ermöglichen.
    \item \textbf{Debugging-Ausgaben:} zur Fehleranalyse und Entwicklung.
\end{itemize}

Alle diese Komponenten sind eng in den Betriebssystemkern eingebunden und wurden gezielt für die Spielentwicklung ergänzt.
Im Folgenden werden die Erweiterungen im Detail beschrieben.

\begin{subsection}{Framebuffer}
Ein \textbf{Framebuffer} ist ein Bereich im Speicher, der direkt die Bildschirmausgabe repräsentiert.
Jedes Byte (bzw. jedes Pixel) im Framebuffer entspricht einem Bildpunkt auf dem Monitor.
Das System zeichnet, indem es Werte in diesen Speicher schreibt.

In MOROS wird der Pointer auf den Videospeicher bereits bereitgestellt.
Unser Framebuffer-Modul kapselt diesen Speicher jedoch in einer \texttt{struct}, die folgende Daten speichert:
\begin{itemize}
    \item Breite und Höhe der Darstellung.
    \item Farbtiefe (hier: 8 Bit, also ein Byte pro Pixel).
    \item \texttt{pitch} (Bytes pro Zeile).
    \item Einen internen Puffer als \texttt{Vec<u8>}, auf dem alle Zeichenoperationen stattfinden.
\end{itemize}

Der Puffer wird über \texttt{flush()} atomar in den tatsächlichen Framebuffer von MOROS kopiert.
So wird immer ein vollständiges Bild ausgegeben, ohne dass während der Berechnung Artefakte entstehen.

Der Framebuffer unterstützt verschiedene Funktionen:
\begin{itemize}
    \item \textbf{Pixel setzen:} direktes Setzen einer Farbe an einer Position.
    \item \textbf{Linien zeichnen:} implementiert mit dem Bresenham-Algorithmus.
    \item \textbf{Rechtecke zeichnen:} sowohl Umrandung als auch Füllung möglich.
    \item \textbf{Kreise zeichnen:} mit oder ohne Füllung.
    \item \textbf{Textausgabe:} mit einem Bitmap-Font, inklusive Skalierung.
    \item \textbf{Bitmaps rendern:} Laden und Zeichnen kleiner Bilder, z.\,B. für Spielfiguren.
\end{itemize}

Damit liefert der Framebuffer die grafische Grundlage für die Darstellung von Spielfeld, Spielern, Bullets und Spielstatistiken.

\end{subsection}

\begin{subsection}{PS/2-Maus}
Für das Zielen und Schießen im Spiel war eine zweite Eingabemöglichkeit notwendig.
Dazu wurde eine vollständige PS/2-Maus-Unterstützung in MOROS ergänzt.

\paragraph{Initialisierung.}
MOROS bietet eine Schnittstelle, um Interrupt-Handler zu registrieren.
Für die Maus wird der IRQ12 (PS/2-Port) über folgende Schritte initialisiert:
\begin{itemize}
    \item Aktivieren des zweiten PS/2-Ports mit Befehl \texttt{0xA8}.
    \item Konfiguration des Controllers und Aktivieren von IRQ12.
    \item Senden des Befehls \texttt{0xF4}, um die Maus in den Datenmodus zu versetzen.
\end{itemize}

\paragraph{Interrupt-Verarbeitung.}
Bei jedem Interrupt werden drei Bytes von den Ports \texttt{0x64}/\texttt{0x60} gelesen.
Diese enthalten Buttons, X-Bewegung und Y-Bewegung.
Die Daten werden in ein \texttt{MouseEvent} umgewandelt, das die Buttons und Bewegungsdeltas enthält.

\paragraph{Ereignis-Queue.}
Da Mausbewegungen asynchron eintreffen, speichern wir sie in einer lockfreien Queue (MPMC).
Der Spiel-Loop kann so jederzeit das letzte Event abfragen oder blockierend auf ein neues Event warten.
Dies entkoppelt die schnelle IRQ-Verarbeitung von der Spiel-Logik.

\end{subsection}

\begin{subsection}{UDP-Erweiterungen}
Für die Netzwerkverteilung des Spiels war UDP entscheidend, da es schnelle und kompakte Nachrichten erlaubt.
MOROS brachte jedoch keine vollständige Implementierung mit.

\paragraph{\texttt{listen}-Methode.}
Eine Funktion \texttt{listen(port)} wurde ergänzt, um einen Socket auf einen Port zu binden.
Ohne diese Methode hätte der Server keine eingehenden Nachrichten annehmen können.
Die Funktion pollt so lange, bis der Socket gebunden ist oder ein Timeout erreicht wird.

\paragraph{Fehler in der \texttt{write}-Methode.}
Die ursprüngliche \texttt{write}-Funktion sendete zwar ein Paket, verließ die Poll-Schleife aber zu früh.
Dadurch konnten Nachrichten mitunter mehrere Sekunden hängen bleiben.
Die korrigierte Version pollt nach dem Senden erneut und stellt sicher, dass das Paket den Stack vollständig verlassen hat.

Diese Änderungen machten eine stabile Echtzeitkommunikation im Spiel erst möglich.

\end{subsection}

\begin{subsection}{Debugging-Ausgaben}
Während der Entwicklung waren Debugging-Funktionen unverzichtbar.
Dafür wurde die Serial-Unterstützung aus \emph{hhuTOSr} übernommen und die Makros \texttt{kprint!} und \texttt{kprintln!} in MOROS integriert.

Damit lassen sich einfache Debug-Ausgaben direkt auf die Konsole schreiben, ähnlich wie \texttt{println!} in Rust.
Diese Ausgaben halfen insbesondere bei:
\begin{itemize}
    \item der Fehlersuche in der Netzwerkkommunikation,
    \item der Verfolgung von Interrupts (z.\,B. bei der Maus),
    \item der Überprüfung der Framebuffer-Ausgabe.
\end{itemize}

Ohne diese Ausgaben wäre die Fehlersuche im Betriebssystemkern erheblich schwieriger gewesen.

\end{subsection}

\end{section}
